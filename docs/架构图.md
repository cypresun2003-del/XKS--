# 软件架构图

本文用四张图说明「第二视角」的软件结构：**分层架构**、**两次模型调用的数据流**、**单条决策记录的状态机**、**数据存储模型**。

代码位置对照：

| 文件 | 职责 | 规模 |
|---|---|---|
| `server/index.ts` | 启动入口：装配 Store 与 Express，按模式挂载 Vite 中间件或 `dist/` 静态资源，监听 `127.0.0.1` | 25 行 |
| `server/app.ts` | 接口层：路由定义、输入校验、并发与幂等控制、错误处理 | 297 行 |
| `server/ai.ts` | 模型调用层：提示词、结构校验、重试策略、画像候选回溯校验 | 147 行 |
| `server/store.ts` | 数据层：SQLite 读写、事务、备份校验与恢复（唯一的数据访问入口） | 154 行 |
| `shared/model.ts` | 前后端共享的 Zod schema（唯一的规则真源） | 155 行 |
| `src/*.tsx` | React 界面与交互 | 17 个文件 |

**分层的关键约束**：`ai.ts` 不直接读写数据库，`store.ts` 不感知模型，`app.ts` 只做编排。所有跨边界的类型都来自 `shared/model.ts`，因此**前端展示的规则和服务端强制的规则是同一份代码**，不存在两边规则漂移的可能。

## 二、两次模型调用的数据流

这是产品的核心机制，也是拆分架构时最先确定的部分。

### 调用①：独立视角（用户点「分析」时立即发起）

```
用户输入
  ├── 当前难题
  ├── 本次情况（一句背景）
  ├── 关联员工的画像描述（可选）
  └── 初步判断  ←────────────── ✗ 不进入请求体
                │
                │  analysisPreview() 用「白名单」显式构造请求字段，
                │  刻意不用对象展开，确保初判、标题、字数、摘要
                │  及其派生内容都无法混入
                ▼
        ┌───────────────────┐
        │  独立请求 payload  │
        │  用户画像          │
        │  本次情况          │
        │  当前难题          │
        │  对相关员工的看法   │
        │  方案数量 = 3      │
        └─────────┬─────────┘
                  ▼
         fingerprint（SHA-256 内容指纹）
                  │
                  ▼
     界面「查看本次发送内容」可逐字段核对 ──► 用户点击确认
                  │
                  ▼
           POST .../analyze
                  │
         ┌────────┴────────┐
         │  服务端二次核对   │  指纹不一致 → 409，绝不发送
         └────────┬────────┘
                  ▼
           DeepSeek / 兼容接口
                  │
                  ▼
          结构校验 + 业务校验
           ├── 必须恰好 3 个角度
           ├── 角度类型两两不重复
           ├── 标题 ≤ 24 字、正文 ≤ 240 字
           ├── 不含人事裁决词（撤换/调岗/裁员/解雇/…）
           └── 画像候选 evidence 必须是原文连续片段
                  │
         ┌────────┴────────┐
      不通过              通过
         │                  │
         ▼                  ▼
   自动重试 1 次      写入分析记录（含发送快照）
         │                  │
    仍不通过 → 502     decision.status = 'analyzed'
    「输入已保留」      revision++
```

**为什么必须拆成两次调用**：同一个会话里模型生成时必然能读到前文，「不参考用户判断」就只是句空话。所以初判**在物理上不出现在调用①的请求体里**——这不是提示词层面的要求，是代码层面的白名单构造。

### 调用②：复盘与画像建议（在用户提交实际反馈之后）

```
用户填写实际结果 + 满意度
        │
        ▼
  reviewPreview() 组装
   ├── 当时的用户画像
   ├── 当时的三个参考角度
   ├── 当时的初步判断
   ├── 我的最终决定 / 认为有帮助的角度
   ├── 我的实际反馈（全文）
   └── 当前可提出更新建议的员工
        │
        ▼
   POST .../reviews/:reviewId/analyze
        │
        ▼
     reviewPrompt
   ├── summary：80–180 字决策复盘
   └── suggestions：有依据的画像调整建议
        │
        ▼
   evidence 回溯校验
   必须逐字出现在「我的实际反馈」原文里，
   否则整次分析不予保存（502）
        │
        ▼
   建议以 pending 状态挂到复盘记录上
        │
        ▼
   用户在界面上逐条 accept / reject
        │
    accept ──► store.addHistory() 记录版本历史
              employee.version++（乐观锁，冲突需重新核对）
    reject ──► 仅标记状态，画像原文不变
```

> **注意**：当前版本的 `analysisPreview()` 中 `risk` 字段固定为 `null`——早期设计里还有一次「风险检查」调用，现已合并进复盘环节，**每次分析只发生一次模型调用**。测试用例 1、5 专门验证了这一点。

## 三、单条决策记录的状态机

`decision.status` 是一个五态枚举，每次流转都由接口层强制校验，**不能跳级**：

```
                    ┌─────────┐
                    │  draft  │  草稿：只写了问题和初判
                    └────┬────┘
                         │ POST .../analyze
                         │ 深度决策要求有效初判
                         │ （「无」「没有」「还没想好」不算）
                         ▼
                   ┌───────────┐
                   │ analyzed  │  已有分析记录，但用户还没表态
                   └─────┬─────┘
                         │
          ┌──────────────┼──────────────┐
          │              │              │
          │ POST .../helpful           │ POST .../finals
          │ 「这个角度有帮助」           │ 拍板：维持原判 / 吸收建议
          │ 仅记录参考，不等于采纳       │
          ▼              │              ▼
    ┌───────────┐        │        ┌───────────┐
    │  helpful  │◄───────┘        │  decided  │
    └─────┬─────┘                 └─────┬─────┘
          │                             │
          │     POST .../reviews        │  拍板时可设回访天数
          │     填写实际结果              │  默认 30 天
          └──────────┬──────────────────┘
                     ▼
              POST .../reviews/:rid/analyze
              生成复盘 summary + 画像建议
                     │
                     ▼
              POST .../reviews/:rid/confirm
              要求：复盘已生成 + 所有建议已处理
                     │
                     ▼
              ┌───────────┐
              │ reviewed  │  复盘确认完成，闭环闭合
              └───────────┘

  另有通道升级分支：
  POST .../upgrade   快速分析 → 深度决策
    · 快速分析（quick）：只用本次情况，可提取临时画像，
      不能拍板、不能回访
    · 深度决策（full）：可关联员工画像、可拍板、可回访复盘
```

**回访队列规则**：拍板时默认 30 天后回访；到期待办；未出结果可延后 14 天；出结果后关闭。旧档案迁移时**不补造事实**，缺失字段一律留空而不是填默认值。

## 四、数据存储模型

SQLite 单文件（`data/zhujian.sqlite`），**5 张表**，业务数据以 JSON 文本列保存、按 Zod schema 读写：

```
settings            key TEXT PRIMARY KEY   data TEXT
  ├── 'context'     用户上下文（称呼 / 行业 / 部门 / 个人介绍）
  └── 'connection'  模型连接配置（baseUrl / model / apiKey）
                    ↑ apiKey 只存服务端，不回传浏览器

employees           id TEXT PRIMARY KEY     data TEXT
  └── Employee      id · alias（员工A/B/…）· nickname · role
                    description（用户的主观描述，非评分）
                    version（乐观锁）· archived · createdAt · updatedAt

employee_groups     id TEXT PRIMARY KEY     data TEXT
  └── EmployeeGroup id · name · employeeIds[] · createdAt

decisions           id TEXT PRIMARY KEY     data TEXT
  └── Decision      见下方嵌套结构

profile_history     id TEXT PRIMARY KEY     data TEXT
  └── ProfileHistory  employeeId · previousDescription · description
                      source（manual / review）· decisionId · createdAt
                      —— 每一次画像改动都留痕，可追溯是谁改的、为什么改
```

`Decision` 的嵌套结构（这是最能体现产品机制的一张图）：

```
Decision
 ├── channel            'trial' | 'quick' | 'full'
 ├── temporaryContext   本次情况
 ├── employeeIds[]      关联员工
 ├── problem / title    当前难题
 ├── initialPlan        用户的初步判断
 ├── originalPlan       最初版本的初判（首次分析时冻结，此后不变）
 ├── revision           乐观锁版本号
 ├── status             五态：draft → analyzed → helpful → decided → reviewed
 │
 ├── analyses[]         每次分析一条，含当时的完整快照
 │    ├── model / requestId / fingerprint
 │    ├── snapshot        发送当时的背景、员工、问题、初判
 │    ├── sentPayload     实际发送出去的请求体（可逐字核对）
 │    ├── result.perspectives[]   三个角度（含 angleType 枚举）
 │    └── profileCandidates[]     快速分析提取的临时画像候选
 │                                （evidence 必须回溯原文）
 │
 ├── helpfulSelections[]  「觉得有帮助」的记录
 │                        source: 'original'（自己的初判）| 'ai'（某个角度）
 │                        明确标注：不代表采纳或执行
 │
 ├── finals[]          拍板记录
 │    ├── mode         'maintain'（维持原判）| 其他（吸收建议）
 │    ├── snapshot     拍板当时的完整快照
 │    └── followup     dueAt / status: pending | done | none
 │
 └── reviews[]         回访与复盘
      ├── outcome / resultStatus / surprise / hindsight / satisfaction
      ├── summary       模型生成的复盘总结
      ├── suggestions[] 画像调整建议（pending → accepted | rejected）
      │                 evidence 必须是反馈原文的连续片段
      └── confirmedAt   用户确认时间
```

**为什么所有内容都存快照**：决策记录的价值在于「当时是怎么想的」。如果关联的员工画像后来被修改了，回看过去那条决策时看到的是**当时的那份描述**，而不是现在的。快照是不可变的，`fingerprint` 就是快照内容的 SHA-256，一旦资料变化，旧分析结果会被拒绝使用而不是悄悄沿用。

**备份与恢复**：`GET /api/backup` 导出包含全部 5 张表结构的 JSON；恢复前 `validateBackup()` 会做全量校验——引用完整性（员工、分析、拍板、复盘之间的 id 是否都能对上）、重复项检查、版本兼容性检查，**任意一条校验失败就整体拒绝，不做部分导入**。

## 五、一句话总结

这套架构只有一条主线：**凡是产品对外承诺的机制，都要在代码里被强制，而不是靠提示词许愿。**

- 承诺「独立视角不读初判」→ 请求体用白名单构造，前端可核对，服务端二次校验指纹
- 承诺「三个角度必须不同」→ 服务端检查枚举重复，重试一次后如实报错
- 承诺「画像建议必须有依据」→ evidence 必须逐字回溯原文，否则整次分析不保存
- 承诺「AI 不替你做决定」→ 状态机不允许跳级，画像改动必须逐条由用户确认
